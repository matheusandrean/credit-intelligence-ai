# Governance

Model risk management, data governance and change-management practices for
Credit Intelligence AI.

## 1. Model Lifecycle

```
generate data -> validate -> feature engineering -> train (baseline + challenger)
    -> evaluate (full metric suite) -> calibrate -> select champion
    -> build scored portfolio -> monitor drift
```

Implemented end to end via `make data validate features train` and tracked
in MLflow (local SQLite backend, `mlflow.db`) — every run logs parameters,
metrics for every split, and the fitted model artifact.

## 2. Champion/Challenger Process

- Both Logistic Regression (baseline) and LightGBM (challenger) are always
  trained and evaluated together (`src/models/train.py`).
- Champion selection rule: highest OOT test ROC-AUC, recorded in
  `models/model_metadata.json` and `reports/model_comparison.json` — never
  silently assumed.
- Calibration method (Platt vs isotonic) is also selected by an explicit,
  documented rule favoring smoothness unless isotonic wins by a material
  margin (see [`MODEL_CARD.md`](MODEL_CARD.md)).

## 3. Monitoring Cadence and Thresholds

Population Stability Index (PSI), computed for both input features and the
model's predicted PD distribution over time (`src/monitoring/drift.py`,
`detect_drift` tool):

| PSI | Status | Action |
|---|---|---|
| < 0.10 | Stable | No action |
| 0.10 - 0.25 | Monitor | Increase review frequency |
| > 0.25 | Potential significant drift | Escalate for model review |

**These thresholds are demonstrative conventions**, not validated against
any real institution's risk appetite — see `configs/project_config.yaml`
and adjust for a real deployment's governance framework.

Portfolio monitoring also tracks vintage/MOB bad-rate curves and roll-rate
migration (`src/analytics/vintage.py`, `src/analytics/roll_rate.py`) to
distinguish genuine deterioration from portfolio growth/seasoning effects.

## 4. Retraining Triggers

Conceptually, in this demonstration, retraining is triggered by:

1. `detect_drift` reporting "Monitor" or worse on a key feature or the
   predicted-PD distribution.
2. A full new synthetic data-generation cycle (different seed/volume).
3. A documented change to the feature-engineering pipeline.

Any of these must re-run the full evaluation suite (`make train` +
calibration) before a new model is considered for champion status — no
change is deployed without a fresh side-by-side comparison.

## 5. Known Limitations (Reject Inference)

This platform trains only on originated accounts — there is no "declined
applicant" population, the classic reject-inference problem in credit
scoring. **This demonstration does not implement or claim to implement
reject inference.** It is disclosed here for transparency, per
[`MODEL_CARD.md`](MODEL_CARD.md) and [`docs/LIMITATIONS.md`](docs/LIMITATIONS.md).

## 6. Independent Validation

No component of this platform — model, calibration, or thresholds — has
undergone independent validation, legal review, or regulatory approval.
See the repository [`LICENSE`](LICENSE) disclaimer.

## 7. Data Governance

- All data is synthetic, generated by versioned, seeded code
  (`src/data/generate_synthetic_credit_data.py`) — see
  [`DATA_CARD.md`](DATA_CARD.md).
- Automated data-quality checks (`src/data/validation.py`) run before
  every training cycle and block on: duplicate IDs, presence of any
  protected attribute, and cross-field consistency failures.
- No dataset — raw, processed, or a trained model binary — is committed to
  git; every artifact is regenerated locally from code (see
  [`SECURITY.md`](SECURITY.md)).

## 8. Change Log Discipline

Commits in this repository are scoped by pipeline stage (`feat: add
synthetic credit portfolio generator`, `feat: add credit risk modeling and
probability calibration`, ...) so the evolution of each governance-relevant
component (model, calibration, thresholds) is independently reviewable in
`git log`.
